01

Why a relational graph, not a graph database

The brief ruled out Neo4j, Neptune, and anything graph-native. Everything here runs on the same Azure PostgreSQL Flexible Server the rest of the project already uses.

SAP Plant Maintenance is naturally a network — a Functional Location contains Equipment, a Maintenance Plan schedules Items against that Equipment, a Task List tells the Item what to do, and Work Orders and Notifications reference all of it. Modelling that as a graph is the right call. Running it on a dedicated graph engine is not, when the data already lives in Postgres and the team already knows SQL.

So the graph is built from four small, generic tables instead of one bespoke table per SAP entity. The payoff shows up every time a new dataset gets added: Functional Location and Equipment shipped first, then Maintenance Plans/Items/Task Lists, then Work Orders and Notifications — and none of those additions changed the schema. Each one is a new node_type, a few new relationship values, and a loader file that looks like the ones before it.

02

The four tables

Every entity, every relationship, every attribute — SAP Functional Location or a Work Order created next year — lands in one of these four tables. No entity ever gets its own table.

TableHoldsKey columns
nodesOne row per entity of any type — a Functional Location, an Equipment, a Work Order…node_id (PK), node_type, natural_key, updated_at
node_propertiesEvery attribute of every node, as name/value pairs (EAV)node_id + property_name (PK), value_text / value_num / value_date
edgesEvery relationship between two nodessource_id, relationship, target_id (unique together)
edge_propertiesReserved for relationship-level attributes — no dataset has needed one yet, so it's emptysame shape as node_properties, keyed by the edge

How the four tables physically connect — one foreign key, in one direction, and edges uses it twice (once as the relationship's source, once as its target):

View the literal CREATE TABLE statementsschema.sql 
CREATE TABLE IF NOT EXISTS nodes (
    node_id     TEXT PRIMARY KEY,
    node_type   TEXT NOT NULL,
    natural_key TEXT NOT NULL,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS node_properties (
    node_id       TEXT NOT NULL REFERENCES nodes(node_id) ON DELETE CASCADE,
    property_name TEXT NOT NULL,
    value_text    TEXT,
    value_num     NUMERIC,
    value_date    TIMESTAMPTZ,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (node_id, property_name)
);

CREATE TABLE IF NOT EXISTS edges (
    source_id    TEXT NOT NULL REFERENCES nodes(node_id) ON DELETE CASCADE,
    relationship TEXT NOT NULL,
    target_id    TEXT NOT NULL REFERENCES nodes(node_id) ON DELETE CASCADE,
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (source_id, relationship, target_id)
);
CREATE INDEX IF NOT EXISTS idx_edges_source ON edges (source_id);
CREATE INDEX IF NOT EXISTS idx_edges_target ON edges (target_id);

CREATE TABLE IF NOT EXISTS edge_properties (
    source_id     TEXT NOT NULL,
    relationship  TEXT NOT NULL,
    target_id     TEXT NOT NULL,
    property_name TEXT NOT NULL,
    value_text    TEXT,
    value_num     NUMERIC,
    value_date    TIMESTAMPTZ,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (source_id, relationship, target_id, property_name),
    FOREIGN KEY (source_id, relationship, target_id)
        REFERENCES edges (source_id, relationship, target_id) ON DELETE CASCADE
);

node_id is always deterministic — a short type prefix plus the SAP identifier, never a random ID. Re-loading the same SAP record always produces the same node_id, which is what makes the whole pipeline safe to re-run:

PatternExampleReads as
FL:<code>FL:BOVA.STU.TOP.PRIMARYFunctional Location BOVA.STU.TOP.PRIMARY
EQ:<code>EQ:30166Equipment 30166
TL:<Group>-<Counter>TL:BODA003-6Task List, Group BODA003, Counter 6 — a composite key, still deterministic

Why EAV for properties instead of a real column per attribute: SAP's own attribute set for Equipment isn't the same as for a Notification, and it isn't fixed even within one entity type over time. EAV means a new attribute is a new row, never a schema migration — the same reason the whole graph is 4 tables instead of dozens.

04

The relationship graph

Thirteen typed, directed edges connect the eight node types. Two of them — FOR_FUNCTIONAL_LOCATION and FOR_EQUIPMENT — are reused by three different record types rather than reinvented per entity, which is the single most load-bearing decision in this design.

Direction rule, applied without exception: structural hierarchy (HAS_SUBFLOC, HAS_EQUIPMENT, HAS_ITEM, HAS_OPERATION) always points parent → child. Every other relationship points from the transactional or planning record to the asset or entity it references — never the reverse. A Work Order points at the Functional Location it was raised against, not the other way around, because the Work Order's own row is what gets re-read on every load; the Functional Location doesn't carry a "current work order" field to re-read.

05

Conventions that make it work

Incremental, never destructive

Every load is a full re-read of the current SAP extract, reconciled against what's already in the graph — insert what's new, update what changed, leave the rest alone. Re-running the same file twice in a row produces zero changes the second time; that's the correctness check we use after every load.

Reconciliation is scoped by whichever side is "re-read"

For structural edges, the child is re-read each load (its parent link can change), so stale-edge cleanup is scoped by the target. For every FOR_*/USES_*/TRIGGERED_* edge, the record itself is what's re-read, so cleanup is scoped by the source. Get this backwards and a moved Equipment or a re-assigned Work Order leaves a stale edge behind instead of being cleanly replaced.

Stub nodes never block a load

A missing reference always becomes a stub, never a dropped edge or a failed load. When the real record eventually appears, it upserts into the same deterministic node_id the stub already used — there's no separate "un-stub" code path, because there's nothing to migrate.

One property, one column, always the same one

SAP occasionally exports the same identifier as a number in one column and as text in another — an Equipment number read as 30166 in one place and "30166" in another, or a Long Text line that happens to look like a bare number. Left alone, that flips a stored value between "30166" and "30166.0" across runs and reads as a spurious change. Every identifier and every text property is normalized through the same conversion before it's compared or stored, so identical SAP data always produces an identical row — a re-run genuinely reports zero changes instead of manufacturing phantom updates.

Five query shapes cover most of what gets asked of the graph day to day:

-- Children of a Functional Location
SELECT target_id FROM edges
WHERE source_id = 'FL:BOVA' AND relationship = 'HAS_SUBFLOC';

-- Parent of a Functional Location
SELECT source_id FROM edges
WHERE target_id = 'FL:BOVA.STU' AND relationship = 'HAS_SUBFLOC';

-- Equipment at a location
SELECT target_id FROM edges
WHERE source_id = 'FL:BOVA.STU.TOP.PRIMARY' AND relationship = 'HAS_EQUIPMENT';

-- Every property of a node
SELECT property_name, value_text, value_num, value_date
FROM node_properties WHERE node_id = 'EQ:30166';

-- One property of a node
SELECT value_text FROM node_properties
WHERE node_id = 'EQ:30166' AND property_name = 'manufacturer';

And the one recursive shape — every descendant of a Functional Location, arbitrary depth, in one query:

WITH RECURSIVE descendants AS (
  SELECT target_id AS node_id, 1 AS depth
  FROM edges WHERE source_id = 'FL:BOKOR' AND relationship = 'HAS_SUBFLOC'
  UNION ALL
  SELECT e.target_id, d.depth + 1
  FROM edges e JOIN descendants d ON e.source_id = d.node_id
  WHERE e.relationship = 'HAS_SUBFLOC'
)
SELECT * FROM descendants;

A ready-to-run version of these — edit one variable, uncomment one function, run — lives in test_queries.py alongside the loaders.
